# 전투 효과 및 AI 중간 상태 저장 최적화 검증

기준은 0.0.7.1 (`4178e2f769b4188fbc87c4030c0907baed7d85c6`)이다. 제품 변경은 `view/anims/player.js`와 `ai/lookahead.js` 두 파일이며, 별도 PR #3의 도감·패널·배경·가방 변경에 의존하지 않는다.

## 실행

README의 vendor 준비 및 의존성 설치를 먼저 수행한다. Node.js 24 이상, Git, 고정된 Pokemon Showdown/PokeRogue vendor와 프로젝트의 Phaser/esbuild를 사용한다. 테스트 전용 새 의존성은 없다.

```sh
node --test tests/*.test.mjs
npm run build
node --check dist/poke-battle.js
```

기준 동작 비교 테스트는 `git show 4178e2f:...`로 원본 모듈을 읽는다. 소스 ZIP만으로는 실행할 수 없으며, shallow checkout에 해당 객체가 없으면 다음과 같이 준비한다.

```sh
git fetch origin 4178e2f769b4188fbc87c4030c0907baed7d85c6
```

독립 브랜치에서 회귀 테스트 32개가 통과했다. 애니메이션 8개, 실제 엔진의 AI 다중 턴 비교 13개, 탐색 분기 및 객체 수명 11개다. 0.0.7.1의 기존 버전·표시 이름을 유지하며 배포 파일은 릴리스 때 빌드한다.

전체 24단계 빌드와 배포 JS 문법 검사도 통과했다. 추가로 PR #3의 제품 소스 5개만 메모리에서 합친 빌드는 누적 opt7 테스트 파일과 바이트 단위로 같았다(6,134,699바이트, SHA-256 `830bfcdb517cbea49d9148e8cf947a26d25182e8d8748bd433f981eb45cc513d`).

## 효과 스프라이트 재사용

한 번의 애니메이션 재생 안에서만 일반 효과(`target=2`)를 재사용한다. 사용하지 않는 unlocked 효과는 숨기고 비활성화하며, 재사용할 때 새 효과와 같은 그리기 순서·상태를 복구한다. 포켓몬 복제(`target=0/1`)의 수명과 locked 효과는 기존 처리대로 유지한다. 완료·중단 시 보관한 효과를 모두 파괴하며 재생 사이에는 보관하지 않는다.

테스트는 실제 player 소스와 Phaser Transform/Alpha/Visible 컴포넌트를 사용한다. 순서·색조·blend·크기·회전·투명도·잠금 상태, 중단·누락 프레임·연속 재생의 정리를 확인한다.

개발 중 별도 원본 비교 결과:

- 전체 1,239개 변형에서 37,369프레임, 278,673개 객체 상태가 일치했다. 효과 생성은 8,359→6,443회(약 22.9% 감소), 포켓몬 복제 생성 2,615회는 동일했다. 이는 전체 corpus의 각 변형을 한 번 재생한 합계다.
- Chrome Phaser 3.90 WebGL/SwiftShader의 22개 재생 조건, 968개 캡처 프레임에서 픽셀 해시가 일치했다. 실제 효과 PNG와 테스트용 포켓몬 텍스처, 제어한 시계·tween을 사용했으므로 실제 Risu 전투 화면이나 FPS 비교는 아니다.
- 같은 재현의 CPU 중앙값 예: darkest-lariat 0.70→0.50ms, thunderbolt 1.30→1.20ms, geomancy 1.70→1.50ms. 대기·오디오를 제외한 처리 비용이며 실제 재생 시간 단축률이 아니다.

## 최고 보스 싱글의 중간 상태 직렬화

원본은 1차 탐색의 모든 유효 reply를 직렬화하지만, 2차 탐색에는 상위 후보 2개의 최악 reply 2개만 사용한다. 이번 변경은 그 상태들만 보관하고 실제 2차 탐색 직전에 직렬화한다. 모든 reply의 평가와 평균, 동점 순서, 시뮬레이션 수, 난수 seed와 판단 정책은 유지한다. ended reply도 최악 순위에 포함한다.

제곱 거리나 JSON clone 등 다른 알고리즘을 도입하지 않는다. `snapshot`/`restore`/`battleFromJSON` 및 탐색 폭 상수는 원본 그대로다. 임시 복사본은 폐기 시 또는 `finally`에서 정리한다.

검증 범위:

- 실제 vendored 엔진에서 30개 전투 시나리오를 여러 턴 진행하며 원본과 비교한다. 일반/최고 보스, 싱글/더블, 2/6마리, 3시드, 독·수면, 중첩 metadata, 초과 IV/EV, 보스 회복 도구 소비, 실제 Mega/Tera 사용, 파트너와 강제 교체를 포함한다.
- 선택·전체 AI 보고서(ms 제외)·복원 횟수, 전투 snapshot/PRNG/HP/PP/상태/요청/protocol과 확정된 AI 저장 상태를 비교한다.
- stub은 모든 분기 seed의 순서, 동점·종료·거부·다음 기술 없음·snapshot/복원/평가 예외와 정리를 비교한다.

개발 중 Chrome 쌍 비교 예시(각 모드 예열 10회 후 30회, 고정 시드 3개, 순서 교대):

| 최고 보스 싱글 | 원본 중앙값 | 변경 중앙값 | 원본 p95 | 변경 p95 |
| --- | ---: | ---: | ---: | ---: |
| 양쪽 2마리 | 54.80ms | 52.00ms | 98.30ms | 105.60ms |
| 양쪽 6마리 | 88.70ms | 74.10ms | 163.50ms | 146.10ms |

이는 독립 Chrome 엔진 재현의 해당 실행 결과다. 실행 간 편차가 있으며 p95는 일관되게 개선되지 않았다. 별도 100표본 비교와 GC 추적에서도 지속적인 p95 회귀·개선을 단정하지 않았다. 실제 Risu FPS 향상률로 해석하지 않는다.

기본 시드의 실제 엔진 계수는 다음과 같았다.

| 항목 | 2마리 원본→변경 | 6마리 원본→변경 |
| --- | ---: | ---: |
| 전체 snapshot | 26→5 | 37→5 |
| lookahead 내 snapshot | 25→4 | 36→4 |
| restore | 95→95 | 106→106 |
| 시뮬레이션 | 89→89 | 100→100 |
| 동시 복원본 최대(실제 전투 제외) | 2→8 | 2→8 |
| 결정 종료 후 복원본 | 0→0 | 0→0 |

내부 검색 복사본 최대 7개에 기존 probe가 더해진 계수다. 실제 peak heap bytes는 측정하지 않았으며 메모리 사용량 감소를 주장하지 않는다. 일반 AI와 더블에는 이 lookahead 경로가 적용되지 않는다.

## 확인 범위와 제한

PC 사용자에게 현재까지 눈에 보이는 동작이 크게 달라지지 않는다는 보고를 받았다. 정확한 파일·모든 기술·조건별 실기 검증 완료로 확대하지 않는다. 모바일은 미확인이고, 실제 Risu FPS·사용자 기기 성능 측정은 없다.

지원되는 정상 상태의 회귀 범위에서 결과가 일치했다. 직렬화를 생략한 탈락 분기에만 직렬화 불가능한 비지원 값이 생긴다면, 원본에서 발생하던 직렬화 예외와 AI fallback이 생략될 수 있다. 선택되어 직렬화되는 분기의 오류 전파와 임시 객체 정리는 테스트한다.

검토 후 채택하지 않은 복원 캐시·복원본 제한 실험 및 스토리 계산의 화면 갱신 양보는 이 변경에 포함하지 않는다.
